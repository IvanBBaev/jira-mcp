Overall: the offline test system is unusually good. It runs 2944 deterministic tests in about 17 s. Every one of the 743 corner-case ids is reached by a real test name, and docs-lint enforces that. The never-replay and write-gate logic are covered almost line for line. The risk lies elsewhere, in two places. First, live proof has fallen behind the surface: it was 40 of 52 at 0.9.4 and is 40 of 82 now, and some of those 40 proofs are stale. Second, the newest safety boundary, project scope, has the weakest tests in the safety core: 59 of its 302 branches are never taken, and checks can be deleted without any test failing. Both are cheap to fix compared with the cost of shipping a scope bypass or a broken write route under a "1.1.0" label. Everything else below is hardening for 2.0.

## Detailed findings

### QA-01 — Live proof has fallen behind the tool surface

**What.** Gate C has proven 40 tools live (27 of 28 reads and 13 writes at the time), all on the 0.9.4 surface, in the 2026-08-17/18 runs. HEAD has 82 tools, so 42 have never touched a real Jira:

- 12 tools from 0.9.4. Seven are blocked by permissions: watcher add and remove, version create and update, component create and update, and issue delete. Five are sprint writes stranded by an over-long sprint name: sprint create, start and close, move to sprint, and move to backlog.
- 6 tools added in 1.0.0: `jira_bulk_delete_issues`, `jira_bulk_edit_issues`, `jira_delete_component`, `jira_delete_sprint`, `jira_delete_version` and `jira_get_bulk_status`.
- 24 tools added since 1.0.0: 10 writes and 14 reads (two of them the portfolio tools), including `jira_rank_issues`, `jira_set_estimate`, `jira_update_sprint`, `jira_update_worklog`, the filter writes, the remote-link writes, `jira_delete_attachment` and `jira_unlink_issues`.

**Stale proofs.** V3-01 moved `jira_get_sprint_issues` and the backlog and summary reads from `/rest/agile/1.0` to `/rest/software/1.0`. A 403 on that root has been reported under some auth modes (ROADMAP V3-21), so the earlier live proof of `jira_get_sprint_issues` no longer describes the code. D148 (version counts), D149 (multi-key get-issue) and D152 (file output) also changed tools that were already proven.

**Evidence.** Manifest snapshot diff across `v0.9.4`, `v1.0.0` and HEAD; `docs/RELEASING.md:293-372`; `docs/IMPLEMENTATION-PLAN.md:55-56` (R04 and R05, both still open). The driver `scripts/verify-live.mjs` names 80 of the 82 tools; only `jira_portfolio_analyze` and `jira_portfolio_report` are absent. All 42 tools are therefore covered by a rehearsal against the fake and by nothing else.

**Why it matters.** Every past live run found 3–4 defects that the fake did not reproduce (`docs/IMPLEMENTATION-PLAN.md:56`). Statistically, a 1.1.0 that adds 24 tools and moves a REST root ships several defects that no offline test can find. The rank, estimate, filter, remote-link and bulk endpoints are exactly the ones where Jira Cloud's real request shapes and permission behaviour differ from the docs.

**Recommendation.** Run one Gate C read and write pass over all 42 tools plus the stale four. Put the result into a generated matrix (QA-R1). Make that pass a hard precondition of V3-22. Add the two portfolio tools to the driver: they are reads composed of tools that are already proven, so the cost is low.

**Acceptance.** Every tool in `manifest.snapshot.json` has a row in a live-proof ledger that records the date, the auth mode and PASS / FAIL / SKIP-with-reason. No tool's last proof predates a change to its route. The `/rest/software/1.0` routes are proven under Basic, scoped-token and OAuth 3LO, or the `/agile` fallback is proven under the modes that 403. The release notes quote the ledger's numbers.

### QA-02 — Project scope: unexercised allow and deny paths in a new safety boundary

**What.** `src/mcp/project-scope.ts` (D400, new since `v1.0.0`; `git cat-file -e v1.0.0:src/mcp/project-scope.ts` fails) is default-deny and routes each request by its REST root. The fresh coverage shows 59 of 302 branches and 47 of 810 lines never executed. The uncovered lines map to specific tools:

| Lines | Route / branch | Tool(s) affected |
|---|---|---|
| 717-725 | `POST /backlog/issue` | `jira_move_to_backlog` (whole branch never run) |
| 718 | sprint `/issue` POST allow path | `jira_move_to_sprint` |
| 703-710 | sprint create via `originBoardId` (allow and deny) | `jira_create_sprint` |
| 736-742 | agile `issue/{key}` with `boardId` | `jira_set_estimate` (new in 1.1) |
| 608-617 | component create, and update/delete with `moveIssuesTo` | `jira_create_component`, `jira_delete_component` |
| 623-624 | version create | `jira_create_version` |
| 588-589, 604-605 | link create and delete allow paths | `jira_link_issues`, `jira_unlink_issues` |
| 680-681 | `createmeta/{project}` | create-metadata read |
| 637, 646 | unknown search and bulk sub-routes (deny) | fail-closed defaults |

**Mutation reasoning.** If you delete `await assertIssues(req, issueRefs(body?.['issues']))` at `:722`, or `await assertIssue(req, second)` at `:738`, or the `moveIssuesTo` check at `:615`, every test still passes, because those lines never run. The rank test at `src/mcp/project-scope.test.ts:437-447` does cover `:728-735`, but it only asserts that some refusal happened (`refused()` at `:36-44` checks the error kind). It does not check that the out-of-scope anchor `XYZ-1` was the reason. A mutation that drops the anchors from `refs` but keeps `ABC-1` out of scope would survive.

**Why it matters.** `JIRA_PROJECTS` is a headline 1.1 safety feature. Users will set it to restrict an agent to one project. A missed check lets that agent move, re-estimate or re-parent issues in other projects. That is a correctness and safety defect, and offline tests are the only line of defence, since Gate C runs in a single-project sandbox.

**Recommendation.** Add a table-driven scope matrix, `src/mcp/project-scope.matrix.test.ts`. It drives every write tool and every scope-relevant read in `PACKAGES` through the real `defineTool` handler with a recording fake, three times: all references in scope (must reach the network), one reference out of scope (must be refused with the out-of-scope key named), and references missing (must fail closed). Make each refusal assertion name the offending key. Add a per-file floor of 100% lines and at least 97% branches for `project-scope.ts` (QA-10).

**Acceptance.** Lines 588-742 are fully covered. Each case removed by mutation (see QA-11) is killed. A new write tool added to `PACKAGES` without a matrix row fails the test (the test iterates the catalogue and keeps an explicit exemption list).

### QA-03 — Read tools are not confined to reads at runtime

**What.** The write gate wraps write tools. For read tools it does `if (call.tool.writeTier === undefined) return call.invoke(call.jira);` (`src/mcp/write-mode.ts:980`), handing over the raw seam. `readOnlySeam` (`:617`) exists, but it is applied only to `planContext` (`:865`, `:1007`). `define.ts:254-264` and `index.test.ts:295` prove that the annotations agree with `writeTier`. Nothing proves that a read-annotated tool's code sends only GET or `safe` requests.

**Why it matters.** Read-only mode, the reader profile and `JIRA_WRITE_MODE=plan` all rely on the "read" label being true. A refactor such as V3-10, V3-12 or V3-24 that accidentally routes a read tool through a mutating spec would pass every test and break the read-only guarantee silently.

**Recommendation.** Pass read tools `readOnlySeam(call.jira)`, so a non-read request throws a typed internal error. Add a catalogue test: for every tool with `readOnlyHint: true`, invoke it with minimal valid arguments against a recording fake that answers 200 to everything, and assert that every recorded request is a GET or a `safe` POST.

**Acceptance.** A read tool modified in a test to send a PUT fails with an internal error and no network call. The catalogue test covers all 42 reads and fails when a new read tool is added without fixture arguments.

### QA-04 — The `safe` flag carries three meanings with no allowlist

**What.** `safe: true` makes a request replayable on 502/503/504 (`src/core/http-util.ts:510-533`). It also lets the request through plan capture (`src/mcp/write-mode.ts:393`, `isReadRequest`) and keeps it out of the mutation journal (`src/mcp/server.ts:213`). It is set at ten call sites: `src/api/search.ts` (6), `shared.ts` (2), `doctor.ts:1196` and `project-scope.ts:434`. Against about 48 mutating specs in `src/api` (28 POST, 10 PUT, 10 DELETE), there are only 36 spot assertions that `safe` is absent.

**Why it matters.** Setting `safe: true` on a single write spec, for example to "fix" a flaky retry, at once turns it into a request that may be replayed, that runs during plan mode and that goes unjournaled. Those are the three invariants the project calls hard rules.

**Recommendation.** Add a structural test that collects every `JiraRequestSpec` builder in `src/api`, or greps the compiled output, and compares the set that carries `safe: true` against a frozen allowlist, each entry with a one-line justification. Changing the list then shows up as a reviewed diff.

**Acceptance.** Adding `safe: true` to any spec outside the allowlist fails the gate with a message that names the spec.

### QA-05 — The fake is unverified, and the recorded corpus is empty

**What.** Almost every behavioural test asserts against hand-authored `jiraOk(...)` bodies or the stateful `scripts/fake-jira.mjs` (4836 lines, excluded from coverage by `.c8rc.json`). `test/fixtures/` holds two synthetic error bodies. `docs/TESTING.md` says the fixture loader is passed explicitly because the corpus is too small. `scripts/record-fixture.mjs` and its PII lint exist and are tested (1429/1597 lines), but they have never been used to build a corpus (`docs/IMPLEMENTATION-PLAN.md:295`).

**Why it matters.** The fake is the oracle. When it is wrong, the tests prove agreement with a mistake. The 3–4 defects per live run are the measured size of that drift. V3-18 plans to split the fake into typed modules, which is the right moment to pin it, and also the moment drift is easiest to introduce.

**Recommendation.** During QA-R1, record a redacted corpus: one success body and one or two error bodies for each of the 82 tools' endpoints, run through the existing PII lint. Then add a contract test that replays each recorded request against `fake-jira` and compares the response shapes (keys, types, pagination fields, error envelope). Values are not compared. Schedule a re-record whenever the live ledger shows a route change.

**Acceptance.** Every endpoint the catalogue uses has at least one recorded fixture. The contract test runs in the gate. A deliberate shape change in the fake (for example renaming `nextPageToken`) fails it.

### QA-06 — The whole-system tests run outside the gate, and live CI is probably idle

**What.** `scripts/rehearse-live.mjs` (passes A–K) and `scripts/rehearse-datacenter.mjs` drive the real built server against the fake end to end. Per `docs/TESTING.md`, they are not part of `npm run check` and not in CI. The `live` job in `.github/workflows/ci.yml` runs `verify-live` in read-only mode once a week and skips with a notice when `JIRA_API_TOKEN` is empty. `docs/IMPLEMENTATION-PLAN.md:24` lists the missing Actions secrets as a blocker. I could not verify the run history (no `gh` CLI on this machine).

**Why it matters.** The rehearsal is the only test that proves the 82-tool server, the gate, scope and transport together. It can rot silently between manual runs. A skipped live job looks green.

**Recommendation.** Add a `rehearse` CI job on Node 22 that builds and runs both rehearsals against the in-process fake. It needs no secrets and costs about a minute. In the `live` job, replace "skip with a notice" by a failure once the last successful live run is older than N days, or at least have it open an issue.

**Acceptance.** Every PR runs both rehearsals. A rehearsal failure blocks merge. The live job's skipped state is visible as an alarm, not as a green check.

### QA-07 — No regression net for the 2.0 renames

**What.** V3-24 renames tools and keeps the old names "hidden but callable through 2.x". No roadmap row creates a test that freezes the old surface. `src/tools/index.test.ts:218` pins the current snapshot, which V3-24 will regenerate, so it protects nothing across the rename.

**Why it matters.** Agent prompts and user configs in the wild reference the current names, along with `JIRA_TOOLS_DENY` and package filters. A rename that drops an alias, changes an alias's input schema or lets an alias escape the deny list or write gate is a silent break for 2.x users.

**Recommendation.** Before V3-24 starts, copy today's `manifest.snapshot.json` to a frozen `test/legacy-surface-1.x.json`. Add a test that, for every 1.x name: (a) resolves to a callable tool, (b) accepts the 1.x input schema, (c) carries the same write tier and annotations, (d) obeys deny, package and scope filters under the old name, and (e) is hidden from `tools/list`.

**Acceptance.** Deleting any alias, or changing its tier, fails the test. The test file is frozen under Rule 2, so a pure move keeps its tests unchanged.

### QA-08 — The wire contract tests use synthetic tools

**What.** V3-06 (`src/mcp/call-time-guard.test.ts`) proves call-time enforcement over InMemoryTransport with `defineTool` fixtures. `server.test.ts:400-414` iterates the `jira_fx_*` harness tools. No wire-level test lists the real `PACKAGES` under each profile and compares the result with the snapshot.

**Why it matters.** The fixtures prove the mechanism. The catalogue could still mis-declare a package membership or a profile mapping that only shows up over the wire.

**Recommendation.** Add one test per profile (default, reader, read-only, plan) that starts the real server over InMemoryTransport with all packages, calls `tools/list`, compares the names against the snapshot-derived expectation, and calls one write per tier to confirm the expected refusal.

**Acceptance.** Moving a write tool to the wrong package, or exposing it in the reader profile, fails the test.

### QA-09 — Wall-clock flakes

**What.** `src/core/clock.test.ts:55` asserts that `sleep(0)` resolves in under 100 ms of real time. `:80` asserts that an abort returns in under 1000 ms. CC-1105 (`src/testing/rehearse-live.test.ts:197-206`) expects the output `'partial'` from a child process killed after 300 ms. Its timer starts at spawn (`scripts/rehearse-live.mjs:916-919`), so under load the child may not have written anything yet.

**Recommendation.** For the clock adapter, assert ordering ("resolves before a 1 s guard timer") rather than an absolute budget. For CC-1105, start the deadline after the child's first stdout byte, or assert the kill and the exit label without the partial output. This is V3-15; do it first, because it hardens every later item's gate.

**Acceptance.** 50 consecutive gate runs under `stress -c <ncpu>` (or equivalent load) pass with no failures in these files.

### QA-10 — Coverage numbers: distortion, thin margin, no per-file floors

**What.** The totals are 97.99% lines (53117/54203) and 94.35% branches (9937/10532), against floors of 97/94/98/97 (`.c8rc.json`, `all: true`). `scripts/rehearse-live.mjs` counts toward the totals at 520/1132 lines, which is 612 of the 1086 uncovered lines repo-wide. `scripts/record-fixture.mjs` adds 168 more. Without the rehearsal script, lines would be 99.1%. Without both scripts, branches would be 95.1%. Meanwhile `project-scope.ts` sits at 80% branches, which a global floor cannot see.

**Why it matters.** The global number is dominated by a script that is tested elsewhere, and the 0.35-point branch margin means one large untested file will fail the gate for reasons unrelated to quality. Safety modules can regress below acceptable levels without the total moving.

**Recommendation.** Exclude `rehearse-live.mjs` from the totals, as is already done for `verify-live.mjs` and `fake-jira.mjs`, or cover it through the QA-06 CI job. Add per-file floors for `src/mcp/{write-mode,project-scope,taint,registry}.ts` and `src/core/{http,http-util}.ts`: 100% lines and at least 97% branches.

**Acceptance.** `c8 check-coverage` fails if any listed safety file drops below its floor. The global totals are reported both with and without the scripts.

### QA-11 — No mutation testing on the safety core

**What.** No mutation framework is configured. Line coverage near 100% on `write-mode.ts` and `http.ts` says the code executes. It does not say that the assertions would notice a changed condition. QA-02 is a measured example of checks that can be deleted without any test failing.

**Recommendation.** Add Stryker (or an equivalent) as a scheduled or manual job, not part of the gate, scoped to `write-mode.ts`, `project-scope.ts`, `http-util.ts`, the never-replay sections of `http.ts`, and `taint.ts`. Set a break threshold for the mutation score and treat each surviving mutant as a test to write.

**Acceptance.** A baseline report exists. Surviving mutants in the listed files are either killed or justified in the report. The score threshold is enforced on the scheduled job.

### QA-12 — CI and test hygiene

The `coverage` job in `ci.yml` repeats the c8 run that the matrix already performs; its own comment concedes this. The running-count comment at `src/tools/index.test.ts:271` has to be hand-edited for every tool added, and has already needed recounts (`f5e6052`). Derive 82/40/11 from the snapshot and drop the duplicate job. Acceptance: one coverage run per CI pipeline, and no hand-maintained counts in test comments.
