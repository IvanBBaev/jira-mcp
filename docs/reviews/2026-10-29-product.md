# Product & Developer-Marketing review — 2026-10-29

Scope: `jira-mcp-ai` as a product. That covers who it is for, why they would pick it over Atlassian Rovo MCP or sooperset/mcp-atlassian, how a new user gets from the README to a first successful call, how discoverable the package is, and whether the roadmap spends effort where users will feel it. Method: I read `README.md`, `docs/index.html`, `docs/ROADMAP.md`, `CHANGELOG.md`, `package.json`, `server.json`, `.claude-plugin/*`, `.github/ISSUE_TEMPLATE/*`, `docs/CONFIGURATION.md` and the owner's `launch-marketing` skill (`SKILL.md`, `references/channels.md`, `references/projects/servicenow-mcp-ai-2026-10.md`; no jira-mcp analysis exists yet). I measured the tree with `wc`/`grep` at `6cd07bd`. Market data comes from the npm downloads API, pypistats, the GitHub REST API, the official MCP registry API and the web, all pulled on 2026-10-29 (URLs in §Sources). Tags: **[V]** verified today, **[S]** secondary source, **[E]** my estimate. The review was read-only apart from this file.

The engineering is far ahead of the product's reach. There are 53.5k production lines, 70.6k test lines, 13.9k doc lines and 82 tools [V]. Against that, organic installs were about 5–6 a week from September to mid-October [V], 0 GitHub stars, and no directory listings at all. The bottleneck is distribution and positioning, not features. Every week spent on refactors or tools before a user can find and trust the package earns nothing. The safety thesis ("cannot do what you did not approve") is real and defensible: CVE-2026-77243 in sooperset proves the market needs it, and V3-06 already proves this server enforces scope at call time. But no visitor reads that story today. Both the README and the landing page open on breadth ("JQL search, issue reads, transitions…"), which is exactly the axis Rovo now wins. One more thing: Rovo's tool list, updated 2026-10-27, has already absorbed several items from the owner's 2026-10-28 "what Rovo lacks" list (sprint lifecycle, deletes, filter listing, a plan-by-default tool). The differentiation is narrower than the notes assume and has to be stated precisely.

## Strengths

- **A real, provable safety differentiator.** The plan/apply gate, the irreversible tier, `JIRA_IRREVERSIBLE_CONFIRM=elicit` (CHANGELOG [Unreleased], D303) and call-time enforcement of packages, read-only mode, `JIRA_PROJECTS` and plan-only mode all exist. The last one is proven by tests (`src/mcp/call-time-guard.test.ts`, V3-06, `306d322`). The market leader shipped a CVSS 8.8 flaw on exactly this point: tool filters were checked only at listing (CVE-2026-77243, fixed in mcp-atlassian 0.22.0) [V].
- **Low-friction auth.** Three required env vars (`JIRA_SITE`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, see `server.json`), no developer app and no consent screen (landing §Install). Rovo's API-token path is off by default and needs an org admin to enable it [S].
- **A `doctor` command** that checks configuration and credentials from a plain terminal (README §Registration). Few competitors have this first-run debugger, and it should be marketed.
- **Honest trust signals.** npm provenance, pinned-version guidance, zero telemetry (landing stat "0 telemetry calls"), a SECURITY.md with private reporting, CodeQL, a threat model, and a public count of what is proven live (README status).
- **Distribution scaffolding already exists.** `server.json` is valid for the registry, `.claude-plugin/plugin.json` has a `userConfig` that stores the token in secure storage, and there is a GitHub Pages landing page with an OG banner and an animated plan→apply transcript (`docs/index.html` `#term`). Most of the work is pressing "publish".
- **Unique composite tools.** `jira_sprint_summary` (stands in for the velocity report, which has no public API), `jira_portfolio_report` (Mermaid duplicate and dependency report), bulk edit/delete and `jira_rank_issues`. Rovo has none of these as of 2026-10-27 [V].
- **Ten read-only prompts** (README §Tools). These are ready-made "jobs" that can be demoed in 20 seconds.

## Detailed findings

### PRD-01 — The advertised product is not the installed product, and the installed one breaks in three days

**What.** The GitHub README, landing page and plugin all describe the `main` catalogue: 82 tools, 11 packages, elicitation, service accounts, portfolio. Every install snippet pins `jira-mcp-ai@1.0.0`, which has 58 tools in 10 packages (`git show v1.0.0:README.md`). The pages also contradict each other: README says "40 of the 80 tools", the landing says "40 of the 82 … The other 21 ship verified offline", the hero badge says "1.0.0 · on npm" next to "82 tools". Separately, V3-01 moved the sprint issue reads to `/rest/software/1.0` because the agile issue routes are "reported removed 2026-11-01". The published 1.0.0 does not have that fix.

**Why it matters.** A visitor who tries the 82-tool product gets 58 tools. On 2026-11-01 three of the most demo-able reads (`jira_get_sprint_issues`, `jira_get_backlog`, `jira_sprint_summary`) stop working for every existing user (the last one is not in 1.0.0). A first impression of "half the tools are missing and the sprint read is broken" cannot be undone by a later launch post. Mismatched numbers also hurt credibility, as `launch-marketing/channels.md` §Universal says ("fix credibility gaps first").

**Recommendation.** Do V3-22 now: bump `package.json`, `server.json` and both `.claude-plugin` manifests to 1.1.0, and generate every count from the manifest. `scripts/generate-readme.mjs` already does this for the tool table; extend it to the status paragraph and the landing figures, or add a docs-lint rule. If V3-21 (the live 403 check) cannot happen before 11-01, ship with the `/agile` fallback the row already asks for.

**Success metric.** 1.1.0 on npm by 2026-10-31. `npm run docs:lint` fails on any count that disagrees with the manifest. No open "sprint read broken" issue after 11-01.

### PRD-02 — Nobody can find it

**What.** The package is not in the official MCP registry, even though `server.json` and `mcpName` are ready. There is no Glama, PulseMCP or Smithery listing claimed, no Docker image, no MCPB, and no awesome-list entry. The repo has 0 stars [V]. Weekly downloads after the first-publish spike (307, which I assume is mirrors and bots [E]) fell to 5–6 a week from September to mid-October. 1.0.0 lifted that to about 50 [V]. For scale, in the same week [V]: `jira-mcp` 825, `mcp-jira-server` 412, `@mcp-devtools/jira` 231, `@aashari/mcp-server-atlassian-jira` 18,334, and `mcp-atlassian` on PyPI 221,324.

**Why it matters.** MCP users find servers through client directories, registries and "awesome" lists, not through npm search. A server that is in none of them is effectively not on the market.

**Recommendation.** In week 1, after 1.1.0: `mcp-publisher publish` (owner, GitHub OIDC namespace `io.github.IvanBBaev`), claim the Glama listing, submit to PulseMCP, open a PR to `punkpeye/awesome-mcp-servers`, submit to the Cursor directory, and add the Claude Code plugin marketplace instructions to the README. In weeks 3–6: Docker image to ghcr (V3-16), then a PR to `docker/mcp-registry` (approved servers appear within 24 h [S]).

**Success metric.** Listed in ≥5 directories by day 14. Directory referrals show up in the GitHub traffic report by day 30.

### PRD-03 — Positioning: stop selling breadth and sell enforcement

**What.** The landing hero reads "Give your AI assistant a real seat in Jira Cloud — JQL search, issue reads, transitions, comments, worklogs, boards and sprints…". The README opens with "An MCP server for Jira Cloud…". Rovo is mentioned zero times in either. Meanwhile Rovo's supported-tools page (last updated 2026-10-27 [V]) lists 52 Jira tools: 27 read, 15 write (including `manageJiraSprint`, which creates, starts, updates and closes sprints), 1 search, 3 delete (admin-enabled), and 6 manage (admin-enabled; `updateJiraScreen` "returns a plan by default"). It also has `executeDestructive` "agent-level confirmation", audit logs and an IP allowlist. Several items on the 2026-10-28 "what Rovo lacks" list are no longer true. Sprint lifecycle is covered. Deletes exist. Filters can be listed. A plan step has begun to appear, on one tool.

**What is still uniquely this server's, as of 2026-10-29:**
1. Every write gated by plan/apply, plus a human confirm through elicitation that the model cannot answer.
2. Call-time `JIRA_PROJECTS` scope and package or read-only restrictions that are *enforced*, not just hidden (V3-06 proof; contrast with CVE-2026-77243).
3. Bulk edit and delete of up to 1000 issues behind that gate.
4. Rank, plus filter create and update.
5. Sprint summary and portfolio reports.
6. Self-hosted, with no Atlassian AI gateway in the path and no org-admin opt-in for API tokens.
7. A Data Center preview.

**Why it matters.** "Never compete on feature/tool count unless you win it" (launch-marketing step 3). Against Rovo's official status, breadth loses. Against sooperset's 6,067 stars, popularity loses. Safety you can verify wins, and it is the one axis where a competitor has a public CVE.

**Recommendation.** Use the hero "The Jira MCP server that cannot do what you did not approve". Sub-line: "Every write is a plan first. Scope is enforced on every call, not just hidden from the menu. Bulk edits, ranks and sprints, on your machine, with your own token." Then add three proof bullets (plan→apply GIF; refused out-of-scope call; elicit confirm) and a dated "When to use Rovo instead" table (§Competitive matrix). Being honest about where Rovo is better (Confluence, hosted, audit logs) builds trust. Re-verify the Rovo column monthly; it is moving.

**Success metric.** README to npm-install conversion is not directly measurable, so use these proxies: stars per 100 unique repo visitors (GitHub traffic) ≥2 [E target], and the share of new issues and discussions that mention "safety", "scope" or "bulk".

### PRD-04 — No visual proof in the README

**What.** The README has no screenshot, GIF or diagram. `docs/assets/` contains only `og-banner.png`. The landing page's animated transcript is good material, but it is text, it is not in the README, and GitHub visitors never see it.

**Why it matters.** Most repo visitors decide within a scroll [E]. A 20-second clip of "plan → *NOT performed* → apply" makes the thesis obvious. The same asset feeds the LinkedIn post, r/mcp, dev.to and the directory listings (channels.md: "≤30 s video/GIF").

**Recommendation.** Script a deterministic recording against `scripts/fake-jira.mjs`, using vhs or asciinema plus agg, so no tenant is needed and the recording is reproducible. Three beats: (1) a plan for a transition and a worklog, (2) a call to an out-of-scope project, refused at invocation, (3) apply, then a re-read. Put it directly under the README title. Optionally record a second clip of the elicitation dialog in Claude Desktop.

**Success metric.** GIF in the README by day 14. The same asset used in ≥3 channels.

### PRD-05 — First-run experience

**What.** Time to first success from the README is about 8–12 minutes for a Claude Code user [E]: mint a token, hand-edit `.mcp.json` or work out `claude mcp add-json`, restart. For Desktop users it is longer, because the README itself warns that PATH issues make launches fail silently. Missing pieces:
- a one-line `claude mcp add jira -e JIRA_SITE=… -e JIRA_EMAIL=… -e JIRA_API_TOKEN=… -- npx -y jira-mcp-ai@1.1.0` command
- documentation for the Claude Code plugin, which already prompts for the token and keeps it in secure storage — arguably the best install path, and invisible
- Cursor and VS Code install deeplinks
- an MCPB bundle for Desktop (V3-17), which removes the PATH problem completely

Positive: only 3 required env vars, and `doctor` exists.

**Recommendation.** Rewrite README §Registration as tabs or a list, one copy-paste block each for Claude Code (plugin, then CLI one-liner), Claude Desktop (MCPB, then JSON), Cursor (deeplink) and VS Code (deeplink). Each block ends with "run `doctor`" and "ask: *what is on my plate this sprint?*" (the `jira_my_work` prompt). That gives the user a first-success moment.

**Success metric.** TTFS ≤3 minutes for the plugin and MCPB paths [E], timed by the owner on a clean machine. Fewer than 1 in 5 new issues are setup or PATH problems.

### PRD-06 — No feedback loop

**What.** Discussions are disabled [V], blank issues are off, and the issue-form contact links send people to spec documents. Zero telemetry is a deliberate selling point and should stay that way. But then the project needs another way to learn who uses it and for what. Today it has none.

**Recommendation.** Enable Discussions and pin "Show your setup: which client, which packages, which write mode". Add a "Questions & ideas" link to `config.yml`. Keep a weekly metrics log (npm weekly, stars, registry and Glama views where shown, traffic referrers) in the local WORKLOG or a small script. Ask each of the first 10 issue authors for a 15-minute call.

**Success metric.** ≥5 setup replies and ≥3 external issues by day 45. 3 user conversations by day 60.

### PRD-07 — Effort keeps compounding while reach stays near zero

**What.** 53.5k production lines, 70.6k test lines and 13.9k doc lines (CORNER-CASES.md alone is 3,856) serve a package with about 50 weekly downloads. The v3 table has 28 rows. V3-10…V3-14 and V3-18…V3-20 (about 33 h [V, from the table]) are internal refactors with no visible user effect. V3-26 (JSM) and V3-24 (2.0 renames) add surface or churn.

**Why it matters.** The marginal tool adds roughly nothing at this level of reach [E]. The marginal directory listing or demo asset adds measurable installs. More importantly, the refactors make sense *for* contributors and users who do not exist yet. They are cheaper to do later, informed by real usage and real bug reports.

**Recommendation.** Make a rule, ideally a DECISIONS row: *no new tools and no non-urgent refactors until R1–R7 in §Proposed roadmap items are done and the day-45 metrics are read.* The exceptions are API removals (V3-01-class), security fixes and first-run work.

**Success metric.** Over the next 6 weeks, ≥70 % of commits touch distribution, docs, first-run or proof assets [E target].

### PRD-08 — The differentiating tools are the unproven ones

**What.** The README says the 42 offline-only tools are "mostly the permission-gated, irreversible and bulk writes". These are exactly the tools the positioning leans on. CLAUDE.md attributes the gap to the test account lacking project-admin or delete rights.

**Recommendation.** The owner creates a Jira Cloud **Free** site (up to 10 users per Atlassian's free plan [S]), where he is site and project admin and holds "Make bulk changes". Then run Gate C `--write --purge` across all write tools, record the live run as a second demo asset, and change the README line to "82 of 82 proven live" (or the true number). This removes the "UNVERIFIED" stigma from the product's main claim.

**Success metric.** Live-proven count ≥75 of 82 by day 30. A dated live-proof log is linked from the README.

### PRD-09 — npm and GitHub metadata

**What.** The `package.json` description is the 1.0 feature list. The keywords lack the terms people search for (`mcp-server`, `claude`, `claude-code`, `cursor`, `agent`, `jira-mcp`, `atlassian-jira`), and lack `rovo`, which does not belong in the name but helps "alternative to" searches. The GitHub About text predates the safety positioning. The name `jira-mcp-ai`: the `-ai` suffix is redundant, but a rename would cost provenance, the registry namespace and the existing installs. **Keep the name**; fix discoverability with metadata and listings.

**Recommendation.** Description: "Jira Cloud MCP server with enforced safety: plan/apply writes, call-time project scope, bulk edit, sprints and rank. Self-hosted, your own token, no telemetry." Keep it ≤160 characters and in sync with `server.json` (which has its own length limit [S]). Add the keywords and topics.

**Success metric.** The package appears on the first npm search page for "jira mcp" by day 30 (check manually).

### PRD-10 — The default surface is too heavy

**What.** Even after D124, `tools/list` is 93,722 characters, about 23k tokens [E, at ≈4 chars/token]. The default package set is `all`. For the typical "Jira from my editor" job, a user pays that context cost on every session, and Claude Code's tool search only partly hides it. V3-25 (a `standard` profile of about 50 tools) and V3-07 (`alwaysLoad` on the hottest reads) are user-visible improvements, but both sit behind refactor rows in the plan.

**Recommendation.** Do V3-07 and V3-25 straight after 1.1.0, as 1.2.0. Publish the context cost per profile in the README ("standard: ≈X k tokens; reader: ≈Y k"). Make it a ratchet (V3-08).

**Success metric.** Default profile ≤50 % of today's `tools/list` bytes. The number is printed in the README.

### PRD-11 — Licence friction

**What.** The project is GPL-3.0-only (`LICENSE`, `package.json`, plugin manifest; it was MIT up to 1.0.0-beta.1). The ICP described below is security-conscious team leads in companies, and in many companies GPL falls into a "needs legal review" bucket. Running an unmodified GPL program as a separate process normally creates no obligation for the user's own code, but approval checklists often do not distinguish that [S/E]. The panel brief itself said "MIT", which shows the licence is not even clear to insiders.

**Recommendation.** This is the owner's call (Open questions §3). If GPL stays, add a FAQ line to the README and landing page ("Running it does not make your code GPL; the licence matters only if you redistribute a modified copy"). Make the Glama listing, which may still show MIT from the beta, say GPL-3.0.

**Success metric.** No "can we use this?" licence issue goes unanswered. Directory listings show the correct licence.

### PRD-12 — Data Center: verify it or stop growing it

**What.** 48 DC tools ship as an "UNVERIFIED preview" behind `JIRA_DATACENTER_PREVIEW=true`. The roadmap says further work waits for "a real host", and V3-27 sets the decision deadline at 2027-06-30. The market facts: DC new subscriptions ended 2026-03-30; existing customers can renew until 2028-03-30; end of life is 2029-03-28 [V, atlassian.com/licensing/data-center-end-of-life]. Rovo does not serve DC. The DC MCP niche has active players (MrRefactoring/atlassian-dc-mcp in the official registry [V]; the owner's notes give b1ff at about 5.2k a week, not re-verified).

**Why it matters.** DC is the one segment where "self-hosted" is a requirement rather than a preference, and Rovo is absent. It is also a shrinking market with a fixed end date and no verification path today. 18 months of preview is the worst of both: it costs maintenance and earns no trust.

**Recommendation.** Get a host instead of waiting for one: run Atlassian's official Jira Software DC Docker image with an evaluation licence [E: a free trial licence is available; owner to confirm terms]. Run the 48 tools once. Then decide by **2026-12-31**, not 2027-06-30: either promote DC to a verified feature and add it to the positioning ("the only Jira MCP with plan/apply on both Cloud and DC" [E — verify against competitors]), or freeze it and drop it in 3.0.

**Success metric.** A decision recorded as a D-row by 2026-12-31.

### PRD-13 — No launch analysis or content

**What.** The owner's playbook requires analysis before any post, and `references/projects/` has no jira-mcp file. The best hook available is timely and factual. In 2026 the most-downloaded open-source Jira MCP server had a high-severity advisory because its tool filter was checked only when listing tools (CVE-2026-77243, CVSS 8.8, fixed in 0.22.0). This server has a test suite proving the opposite (V3-06).

**Recommendation.** Run `launch-marketing` and save `jira-mcp-ai-2026-11.md`. Lead article for dev.to and r/mcp: "Your MCP tool filter is a menu, not a lock" — a general engineering lesson that names the advisory neutrally and credits the fix, then shows a 10-line test any server author can copy, with this server as the worked example. Next, a LinkedIn carousel ("Would you let an agent bulk-edit 1,000 Jira issues?"). Show HN only in that general framing (channels.md: MCP Show HNs have a median of about 2 points). Owner approval before any post.

**Success metric.** Article live by week 4. ≥50 GitHub visitors from it in its first week (traffic referrers).

### PRD-14 — The plugin ships no skills

**What.** ROADMAP §2 already notes that `.claude-plugin/` holds only manifests. The 10 prompts are valuable, but many clients bury prompts.

**Recommendation.** Add two skills, `standup` and `release-notes`, that call the existing prompts and tools. This makes a plugin install useful on day one and gives the Claude Code marketplace listing something to show.

**Success metric.** Two skills shipped and demoed in the GIF or README.

### PRD-15 — Sustainability

**What.** Donations only (Sponsors, Ko-fi, Donatree), no paid tier, no hosted version. With fewer than 100 weekly installs, any pricing is premature.

**Recommendation.** For 90 days, optimise for users, not revenue. Paths worth revisiting at ≥10 known team users [E]: paid team onboarding or support (setup, scoping policy, sandbox Gate C runs), sponsorware for the DC edition if DC becomes verified, or a "commercial-friendly licence" (dual licence) if the GPL question in PRD-11 comes up from buyers. Do not build a hosted version: self-hosting is the differentiation.

**Success metric.** At least one inbound "can we pay for support?" by day 90, or a documented decision not to pursue revenue.

**Takeaway.** Use Rovo if you want Confluence plus Jira hosted by Atlassian with audit logs. Use sooperset if you want Jira plus Confluence on DC and popularity. Use **jira-mcp-ai** if an agent will *write* to your Jira and you need it unable to touch the wrong project, to bulk-edit without a preview, or to delete without a human ticking yes, all without asking your org admin.

**ICP and jobs-to-be-done.** The target user is the senior engineer or tech lead at a company on Jira Cloud who already uses Claude Code or Cursor and wants the agent to *act* in Jira, not just read it. Their jobs: move tickets and log work as part of coding, groom and rank the backlog, bulk-retag or clean up after a reorg, prepare sprint reviews and release notes. Their blocker is fear of a runaway write, plus no admin rights to enable Rovo's API-token or delete groups. A secondary ICP is the scrum master or PM who needs sprint summary and portfolio duplicate reports. That segment is smaller and less technical, so it is not the launch audience.
